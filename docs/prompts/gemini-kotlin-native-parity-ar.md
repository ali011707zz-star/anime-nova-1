# برومت Gemini لإعادة كتابة تطبيق Anime NOVA الأصلي بـ Kotlin Native

انسخ النص التالي إلى Gemini بعد فتح مستودع Anime NOVA كاملًا لديه:

---

أنت مهندس Android Native خبير. أريد إعادة كتابة تطبيقي Anime NOVA الأصلي نفسه بلغة Kotlin وAndroid Native باستخدام Jetpack Compose وMedia3، ليعمل بسلاسة على الهاتف وAndroid TV. تطبيق Anime NOVA الحالي في المستودع هو المنتج المرجعي وسلوكياته وميزاته هي المطلوب نقلها. يوجد أيضًا كود Kotlin أولي في مجلد اسمه `nova2-android`؛ هذا مجرد مسار/نقطة بداية تقنية داخل المستودع، وليس منتجًا منفصلًا اسمه Nova 2. أكمل إعادة كتابة التطبيق الأصلي واحتفظ بهويته وميزاته، ولا تكتفِ بتغيير الاسم أو إنشاء نموذج جديد.

## 1. حدود المشروع ومصادر الحقيقة

- المنتج المستهدف هو Anime NOVA الأصلي؛ تطبيق `artifacts/nova-mobile` هو المرجع الأول لسلوكه وشاشاته وميزاته، والمطلوب إعادة كتابته Native بـ Kotlin.
- افحص كود Kotlin الأولي الموجود في `nova2-android` وأعد استخدام الأجزاء الصالحة عند الحاجة، لكن لا تعتبره منتجًا جديدًا أو نهائيًا باسم Nova 2. لا تنشئ تطبيقًا موازيًا ولا تحذف أو تستبدل التطبيق الأصلي قبل اكتمال النقل والتحقق.
- الخادم الفعلي مستقل عن Replit. Replit مساحة تحرير فقط. لا تشغّل التطبيق أو تثبّته أو تبنِ APK داخل Replit، ولا تنشئ أو تشغّل workflow محليًا.
- لا تتصل بالـVPS تلقائيًا. إذا احتجت تشخيص الخادم، اطلب إذنًا صريحًا، واستخدم معلومات للقراءة فقط. لا تثبّت أو توقف أو تعيد تشغيل خدمات، ولا تعدّل ملفات أو قاعدة بيانات.
- لا تضع كلمات مرور أو مفاتيح SSH أو API tokens في البرومت أو الكود أو السجلات أو ملفات المشروع. لا تقرأ أو تطبع `.env` أو بيانات الأسرار.
- هوية تطبيق Android الأصلي في `artifacts/nova-mobile/app.json` تشير إلى `com.nova.anime`؛ تحقق منها مقابل إعدادات الإصدار والتوقيع وGitHub CI وبوابة الخادم قبل اعتماد هوية البناء Native. لا تستخدم `com.nova.anime.nova2` أو `nova2-android` كهوية إصدار للتطبيق الأصلي لمجرد أنها موجودة في المسودة. تغيير `applicationId` أو التوقيع قد يمنع تحديث التطبيق الحالي؛ لا تغيّره دون تحقق وموافقة صريحة، ولا تتجاوز بوابة الإصدار/المصادقة.
- لا تضف endpoints أو بيانات أو ميزات افتراضية. افحص كود العميل والخادم والعقود الموجودة أولًا. التقارير القديمة قد تكون منتهية؛ عند التعارض، بيّن التعارض واتبع التنفيذ الحالي والعقد المثبت في الكود.

### الخادم والعقود

- افحص فقط ملفات المصدر ذات الصلة تحت `artifacts/api-server/src` والأنواع المشتركة عند الحاجة لتأكيد أسماء الحقول والمسارات.
- راجع `docs/research/NOVA1_ANALYSIS.md` و`nova2-android/CONTRACTS.md` باعتبارهما مراجع مساعدة، لا ضمانًا بأن كل تفصيل ما زال مطابقًا للإنتاج.
- لا تحاول تجاوز قيود الموقع أو المصادقة أو بوابة الإصدار، ولا تنفذ استخراجًا أو فك حماية لمصادر غير مصرح بها. استخدم فقط تدفق المصادر الذي يقدمه خادم NOVA.

### مخرج مرحلة الفحص

قبل التعديل، أنشئ في ردك جدول توافق يحتوي الأعمدة التالية:

1. الميزة/الشاشة في التطبيق الحالي.
2. ملفات المصدر الفعلية التي تثبت السلوك.
3. وضعها في Kotlin: مكتملة، جزئية، غير موجودة، أو غير مؤكدة.
4. عقد API المطلوب ومصدر إثباته.
5. خطوات التنفيذ والاختبار.

اذكر بوضوح ما لم يمكن التحقق منه. لا تملأ الفجوات بالتخمين. بعد الجدول، نفّذ التغييرات المطلوبة على دفعات صغيرة، مع تحديث الجدول عند اكتمال كل دفعة.

## 3. نطاق التوافق الوظيفي المطلوب

طابق ميزات النسخة الحالية بحسب ما تثبته ملفاتها، مع مراعاة الحالات التالية:

- بدء التطبيق، تحميل الإعدادات البعيدة، إنشاء/تجديد anonymous token، استعادة جلسة المستخدم، وحالات التحميل والخطأ وإعادة المحاولة.
- تسجيل الدخول، التسجيل، إرسال رمز التحقق، تسجيل الخروج، وحفظ بيانات الجلسة بأمان.
- الصفحة الرئيسية وأقسام المحتوى التي تعرضها النسخة الحالية، بما فيها المحتوى الشائع/الرائج/الموسمي/الجاري، أحدث الحلقات، وأقسام الأنمي المدبلج والرسوم المتحركة. لا تثبّت أسماء الأقسام أو endpoints قبل فحص تنفيذها الحالي.
- التصفح حسب النوع والتصنيفات والفلاتر والصفحات؛ البحث وسجل البحث وفلاتره، بما في ذلك البحث بالصورة إن كان تدفقه الحالي قابلًا للنقل بعقد الخادم.
- صفحة التفاصيل: العناوين بلغاتها المختلفة، الملصق والخلفية والبيانات والملخص، قوائم الحلقات/المواسم، المفضلة، التوصيات، التعليقات، وأزرار متابعة المشاهدة بحسب ما يفعله المصدر.
- مسارات المحتوى المختلفة لا يجوز دمجها افتراضيًا في مسار واحد إذا كانت ملفات التطبيق تستخدم API أو نموذج حلقات/مواسم مختلفًا: الأنمي، الرسوم/الأنيميشن، المدبلج، ومصادر StarDima أو غيرها. افحص التدفقات قبل التصميم.
- قائمة الحلقات: العناوين والترقيم والمواسم والصفحات، الانتقال للحلقة السابقة/التالية، واستعادة المسار الصحيح عند الرجوع.
- الأخبار والجدول والتعليقات والملف الشخصي والإعدادات وربط التلفاز والتنبيهات/الإشعارات، بالقدر الموجود في التطبيق الفعلي وبعقود الخادم.
- المفضلة وسجل المشاهدة والتقدم: حفظ محلي، مزامنة الحساب عند تسجيل الدخول إن كان المصدر يفعل ذلك، عدم خلط بيانات المستخدمين، وحل التعارضات أو الحذف المؤجل كما في التنفيذ الحالي.
- التنزيلات: حالة التنزيل والتقدم والإيقاف والاستئناف والإلغاء والحذف والتشغيل المحلي والحفظ إلى المعرض إذا كان مدعومًا. لا تدّع دعم HLS دون إثبات عقد تنزيل offline حقيقي من الخادم. لا تحوّل روابط البث العشوائية إلى تنزيلات مباشرة.
- حافظ على الإبلاغ عن الأخطاء وحالات الاتصال، لكن لا تسجل URLs الموقعة أو tokens أو رؤوس المصادقة.

## 4. مواصفات المشغل — افحص RiftPlayer كاملًا قبل التنفيذ

`components/RiftPlayer.tsx` مع ملفات `app/watch.tsx`, `app/animation/watch.tsx`, `app/dubbed/watch.tsx` هو مرجع سلوك المشاهدة. افحص JSX ومعالجات اللمس والحالة والتخزين المحلي، ولا تكتفِ بأسماء الأزرار. انقل ما هو موجود فعلًا، مع الحفاظ على تجربة Native سلسة:

- تشغيل Media3/ExoPlayer لتدفقات HLS وMP4 التي يسمح بها الخادم، مع headers اللازمة لكل طلب، ونوع الوسيط الصحيح، ومعالجة الروابط المؤقتة. لا تسجل الرابط الكامل.
- استقبال المصادر تدريجيًا إذا كان الخادم يرسل SSE؛ اعرض ما وصل دون انتظار اكتمال المسح، مع إلغاء العمل عند مغادرة الشاشة أو تبديل الحلقة، ومنع وصول نتائج متأخرة إلى شاشة أخرى.
- عرض المصدر والجودة، اختيار مصدر آخر، ترتيب المصادر حسب البيانات الفعلية، وإتاحة الرجوع التلقائي إلى مصدر آخر عند الفشل/التوقف. حافظ على موضع المشاهدة عند تغيير المصدر متى أمكن، ولا تسمح برسائل خطأ مبكرة تلغي فرصة وصول مصادر إضافية.
- حالات واجهة مفهومة: تجهيز المصادر، التحميل، التخزين المؤقت، جاهز، انتهى، فشل، لا توجد مصادر، إعادة المحاولة، ومصدر بديل. لا تعرض الخطأ على أنه «لا توجد نتائج» إذا كان السبب شبكة أو مصادقة أو خطأ تحليل.
- إظهار وإخفاء عناصر التحكم تلقائيًا، التشغيل/الإيقاف، شريط تقدم قابل للسحب، الوقت المنقضي/المتبقي، seek بالنقر/السحب، وتحديث حالة التشغيل بشكل موثوق.
- الإيماءات المحمولة كما يثبتها الكود: النقر المزدوج على جهتي الفيديو للتقديم/الرجوع بمقدار قابل للضبط، وقيمة افتراضية 10 ثوانٍ إذا أكدها المصدر؛ والسحب الرأسي للتحكم في صوت النظام/السطوع مع إظهار مؤشرات مرئية. لا تغيّر السلوك أو اتجاه الإيماءة تخمينًا.
- سرعة التشغيل، تفضيل السرعة، الضغط المطوّل المؤقت إن وجد، كتم الصوت، وقفل عناصر التحكم/فتحها.
- خيارات ملاءمة الصورة التي يدعمها المصدر (contain/cover/fill)، تدوير/عكس الصورة أو لقطة الشاشة إذا كانت متاحة في التنفيذ الفعلي؛ انقل الميزة فقط إذا أمكن دعمها Native فعلًا وبصلاحيات سليمة.
- مسارات الترجمة المضمنة والمنفصلة، اختيار اللغة، تعطيل الترجمة، العربية والإنجليزية حسب المتاح، حالات التحميل والخطأ، وضبط التوقيت بخطوة وحدود مماثلة لما يثبته المصدر.
- أي إعدادات لتنسيق الترجمة أو الترجمة التلقائية/المخزنة أو اختيار مصدر الترجمة يجب أن تُنقل فقط بعد تتبع مصدرها وعقد API والتخزين في الكود الحالي. لا تنشئ ترجمة وهمية أو endpoint جديدًا.
- تخطي المقدمة/الخاتمة عندما تتوفر أوقاتها الصحيحة، إظهار زر التخطي في الفترة المناسبة، وعدم تشغيل التخطي تلقائيًا دون موافقة المستخدم إذا كان التطبيق لا يفعل ذلك.
- انتهاء الحلقة: عدّ تنازلي للتشغيل التالي وإلغاؤه، الانتقال للحلقة التالية/السابقة، اختيار حلقة، ومراعاة نهاية الموسم/السلسلة.
- استئناف الموضع وحفظه عند الخروج/تغيير الحلقة، لا من polling عشوائي يكتب باستمرار. احمِ الحالة عند إعادة إنشاء الشاشة أو تدوير الهاتف.
- زر الرجوع، وضع ملء الشاشة، السطوع، safe areas، وواجهة اللمس يجب ألا تتداخل مع إيماءات Android أو عناصر النظام.
- حافظ على أي ميزات فعلية إضافية تكشفها مراجعة الملف، ولا تعتبر القائمة أعلاه بديلًا عن قراءة `RiftPlayer.tsx` كاملًا.

## 5. الهاتف والتلفاز — واجهة واحدة ملائمة لكل جهاز

- تطبيق واحد Native؛ لا تنشئ تطبيق TV منفصلًا. استخدم Compose وCompose for TV/Media3 بما يتسق مع البنية الموجودة في `nova2-android`.
- الهاتف: أهداف لمس مريحة، قوائم قابلة للتمرير، كثافة مناسبة، دعم RTL، تغيير اتجاه الشاشة للمشاهدة فقط وفق سلوك المرجع، وإرجاع اتجاه الشاشة بأمان عند مغادرة المشغل.
- التلفاز: استخدم نوع واجهة Android TV الفعلي/ميزات الجهاز، لا تعتبر الهاتف تلفازًا لمجرد أن عرضه كبير أو أنه في الوضع الأفقي.
- كل زر وبطاقة وفلاتر وقائمة على التلفاز يجب أن تكون قابلة للتنقل بالكامل بالريموت/D-pad، مع ترتيب focus منطقي، مؤشر focus واضح، حفظ موضع التركيز بعد الرجوع، تمرير الصف إلى العنصر المركّز، وعدم وجود شاشة لا يمكن الخروج منها بزر Back.
- أحجام النصوص والأزرار والمسافات يجب أن تقرأ من بُعد؛ لا تستخدم كثافة الهاتف مباشرة على شاشة التلفاز. اختبر اتجاه RTL والتركيز في القوائم الأفقية والرأسية والنوافذ المنبثقة.
- دعم لوحة مفاتيح التلفاز/الهاتف للبحث، مع إمكانية فتح النتائج والفلاتر بالريموت. لا تشترط شاشة لمس على Android TV.
- افحص `AndroidManifest.xml` وplugins و`NovaResponsive.kt` و`NovaNavGraph.kt` قبل تعديل وضع TV أو الفوكس. تجنب استيراد عناصر Compose TV غير المتوافقة مع إصدار المكتبات الحالي؛ اتبع الحل الموجود أو وثّق سبب تغييره.

## 6. عقود API والأمان

ابدأ من `nova2-android/CONTRACTS.md` و`core/network/NovaApiClient.kt` و`core/model/NovaModels.kt`، ثم طابق العقود مع المصدر الحالي. المسارات الموثقة حاليًا تشمل config والمصادقة، AniList، metadata، عناوين الحلقات، الترجمة، subtitle tracks، جلب مصدر واحد، SSE للمصادر، HLS/video/segment proxies. لا تفترض شكل JSON مختلفًا عمّا يقرأه الخادم.

- احتفظ برؤوس هوية التطبيق التي يضيفها `NovaApiClient`، وanonymous/user tokens حسب حالة الجلسة. لا تُضمّن token ثابتًا في التطبيق ولا تتجاوز release gate.
- احفظ tokens عبر المخزن الآمن الموجود، وتعامل مع الانتهاء/التجديد والتسجيل بالخروج كما هو محدد في الكود. لا تطبع القيم في Logcat أو Crash reports.
- ميّز بين timeout، انقطاع الشبكة، HTTP status، JSON غير صالح، استجابة فارغة، فشل الخادم، وحالة `OFFICIAL_APP_REQUIRED`.
- استخدم timeouts وإلغاء coroutines وsingle-flight/منع الطلبات المكررة عند الحاجة، مع احترام حدود الخادم.
- لا تغيّر schema أو endpoint للخادم لمجرد تسهيل الواجهة. إن كانت ميزة لا تعمل بعقد موجود، وثّق الفجوة واسأل قبل أي تغيير backend.

## 7. أسلوب التنفيذ داخل مشروع Kotlin

- واصل استخدام كود Kotlin الأولي في `nova2-android` حيث يكون صالحًا لإعادة كتابة التطبيق الأصلي، لكن اجعل المنتج والهوية النهائية Anime NOVA الأصلي لا تطبيقًا منفصلًا باسم Nova 2. لا تستبدل المكتبات أو تعِد تنظيم المستودع على نطاق واسع دون حاجة موثقة.
- أبقِ الشبكة والتخزين في repositories، وحالة الشاشة في ViewModels/StateFlows أو النمط المتبع، والواجهة Compose. لا تطلق طلب HTTP أو عملًا طويلًا مباشرة من Composable.
- لا تنشئ Player/ExoPlayer جديدًا مع كل إعادة تركيب Compose. امتلكه وحرره بوضوح، اربط دورة حياته بالشاشة، وتأكد أن تبديل المصدر/الترجمة لا يسبب سباقًا أو تحريرًا مزدوجًا أو تسربًا.
- استخدم مفاتيح ثابتة للقوائم، حالات loading/error/empty/retry، ومعالجة RTL وaccessibility ووصف الأزرار.
- ابدأ بالأجزاء المشتركة ذات أعلى أثر: نماذج البيانات/العقود، نموذج حالة المشاهدة، إدارة Media3، ثم عناصر التحكم، ثم ربط تدفقات الأنمي/المدبلج/الأنيميشن.
- لا تحذف عملًا قائمًا أو بيانات المستخدم أو ملفات أرشيفية. لا تضع ملفات جديدة في الأرشيف لمجرد تجاوز خطأ.
- قبل تعديل build أو dependencies، افحص الإصدارات الحالية في `build.gradle.kts` والـworkflow الموجود. لا ترفع AGP/Kotlin/Media3 أو تغير applicationId من دون حاجة موثقة وموافقة.

## 8. فحص الـVPS (اختياري، قراءة فقط)

الـVPS بيئة تشغيل منفصلة وليس مكانًا لبناء تطبيق Android. لا تتصل به تلقائيًا ولا تطلب مني لصق كلمة مرور SSH في Gemini. إذا طلبت منك تشخيصه صراحةً:

- استخدم وصولًا آمنًا ومؤقتًا فقط، ولا تخزن بيانات الدخول في الملفات أو السجل.
- اجعل كل الأوامر للقراءة فقط، مثل `uptime`, `df -h /`, `free -h`, `pm2 list`, و`systemctl is-active nginx`.
- لا تقرأ `.env` أو قواعد البيانات أو ملفات الأسرار؛ لا تطبع سجلًا قد يحتوي tokens أو روابط بث موقعة.
- لا تستخدم `pm2 restart/delete`, `systemctl restart`, `kill`, `npm/pnpm install`, deploy, build أو أي أمر كتابة/تغيير.
- افصل بين «العملية ظاهرة online» وبين تأكيد أن API أو تشغيل الفيديو يعمل؛ لا تدّع نجاحًا وظيفيًا دون اختبار آمن ومصرح به.
- أبلغني بالنتائج والحدود، واترك أي إصلاح أو إعادة تشغيل لي بطلب وموافقة منفصلين.

## 9. التحقق ومعايير الإنجاز

لا تقل «اكتملت المطابقة» اعتمادًا على وجود الملفات أو نجاح compile فقط. لكل شاشة وتدفق، اربط نتيجة الاختبار بميزة محددة.

تحقق من:

1. البناء الحالي بالطريقة المصرح بها للمشروع، لا من خلال تثبيت/تشغيل التطبيق في Replit.
2. التنقل، RTL، جلسة anonymous وتسجيل الدخول/الخروج، البحث والفلاتر والتفاصيل والحلقات.
3. تدفق مصادر حقيقي من API المسموح: وصول المصادر تدريجيًا، HLS وMP4، headers، تبديل المصدر، retry، الترجمة، استعادة التقدم.
4. تنزيل MP4 المدعوم فقط، الحالات المحلية، المفضلة/السجل والمزامنة إن وجدت.
5. الهاتف باللمس، الدوران والدخول/الخروج من المشغل، ثم Android TV فعليًا بالريموت: D-pad وBack والبحث والفوكس.
6. حالات الشبكة البطيئة/انقطاعها، الحلقة بلا مصادر، مصدر يفشل، تغيير الحلقة سريعًا، وإغلاق المشغل أثناء SSE/تحميل ترجمة.
7. لا توجد tokens أو URLs موقعة في logs، ولا أخطاء lifecycle/تسريب Player.

إذا لم يتوفر جهاز أو API أو CI للاختبار، اذكر ذلك بوضوح ولا تدّعِ أن السلوك تم اختباره. في النهاية أعطني:

- ملخصًا لما أُنجز.
- جدول الميزات المكتملة/الجزئية/غير المدعومة وسبب كل فجوة.
- الملفات التي تغيرت ولماذا.
- أوامر الاختبار التي نُفذت ونتائجها، مع توضيح ما لم يُنفذ.
- أي موافقة أو عقد backend مطلوب للخطوة التالية.

ابدأ الآن بمرحلة فحص المستودع وجدول التوافق، ثم أكمل على دفعات صغيرة دون تغيير تشغيل الـVPS.
